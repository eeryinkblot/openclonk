# OpenClonk 9.0-alpha-fork.1

The first tagged release of [`eeryinkblot/openclonk`](https://github.com/eeryinkblot/openclonk),
a fork of [`openclonk/openclonk`](https://github.com/openclonk/openclonk) carrying
116 commits on top of upstream master (`36de79954`, 2026-04-28).

**What the version number means.** The engine still reports `9.0-alpha`, because
that is upstream's version and this fork does not change what content may ask of
it — `C4XVER1`/`C4XVER2` are checked against every definition's `RequireVersion`,
so a lower number would start rejecting the game's own objects. The `-fork.N`
suffix counts releases of this fork and nothing else. Upstream has been on
`9.0-alpha` since 2018.

## Why this fork exists

OpenClonk does not build on Apple Silicon, and upstream is dormant: roughly one
merged pull request a year, and outside contributions sitting untouched for
years. Its own CI died with travis-ci.org and an AppVeyor image pinned to Visual
Studio 2017, so nothing had verified a build since about 2020.

Fixing the macOS build was the entry point. Most of what it turned up was not
macOS-specific: `c4group` wrote empty archives and reported success, `ctest`
passed while skipping its largest suite, the `groups` target raced against
itself, and the scenario test suite had been running zero assertions because the
player file it was given had never existed. Those defects were platform-neutral
and years old. What hid them was the absence of anyone running the thing.

## What is in it

31 changes against upstream, each one documented in `fork-notes/divergence.md`
with what it does and why upstream's version was wrong.

**The engine runs on Apple Silicon.** `HEADLESS_ONLY` could not configure on
macOS at all, `openclonk-server` hung in an AppKit loop before printing
anything, bundles were unusable on arm64 because `install_name_tool` invalidated
the signatures the kernel insists on, every mouse event was discarded in
fullscreen, Apple's deprecated OpenAL was linked instead of a real one (so no
EFX), and arm64 builds announced themselves as `mac-x86`.

**Seven defects that reported success while failing.** `c4group` exited 0 after
writing zero-byte archives and after failing outright; `ctest` skipped the
`tests` binary because it was declared without `add_test()`; the `groups` target
picked the same temporary filename twice under `make -j` and lost a group; a
packed directory's temporary filename was read after its scope ended; writing a
group without a sort list looked like a write failure; the app bundle's resource
seal never matched, which blocks notarisation; and installing an unrelated
Homebrew package could silently break the audio link. This class is the reason
the CI checks outputs rather than exit codes.

**Build-system fixes on platforms where the options had never been used.**
`HEADLESS_ONLY` had never been tried on macOS, `C4GROUP_TOOL_ONLY` never on
Windows. Both are usable now. The CMake floor moved to 3.10, the language
standard to C++17, googletest to 1.14.0 — below which the library itself no
longer compiles on a current toolchain — and the editor builds against **Qt6**
as well as Qt5, which is what makes an editor on macOS possible at all.

**Continuous integration, from nothing.** Nine jobs, all green: headless builds
with unit tests, packing and the scenario suite on Linux, macOS and Windows; a
client with the Qt editor and mape built and *launched* under Xvfb against both
Qt5 and Qt6; an ASan/UBSan run; a content lint over all 99 scenarios; the macOS
app bundle built and its signature and resource seal verified; and
`C4GROUP_TOOL_ONLY` on Windows, where it can actually fail.

**Tests.** 101 unit tests over four binaries, including new coverage for
`C4Group`, `C4Real` and `C4Random` — the units determinism rests on. The
scenario suite executes **912 assertions** on all three platforms and they agree
assertion for assertion, including which 14 fail. Every scenario's script-link
result is pinned, so a new warning anywhere in `planet/` fails the build.

## Downloads

These are CI build outputs, published because a build nobody can download is a
build nobody can check. They are **not an installer** and not a supported
distribution.

| Asset | What it is |
| --- | --- |
| `…-game-data.tar.gz` | The 13 packed groups, `Music.ocg` included. Needed by every binary below. |
| `…-client-linux-x86_64-qt5.tar.gz` | `openclonk` with the Qt5 editor, plus `mape`. |
| `…-client-linux-x86_64-qt6.tar.gz` | The same built against Qt6. |
| `…-tools-linux-x86_64.tar.gz` | `openclonk-server`, `c4group`, `c4script`. |
| `…-tools-macos-arm64.tar.gz` | The same three, Apple Silicon. |
| `…-tools-windows-x64.zip` | The same three, with the vcpkg runtime DLLs they need. |
| `…-app-macos-arm64.zip` | `openclonk.app`. See the warning below before downloading it. |

Built `RelWithDebInfo`, unstripped and deliberately so: a crash in a fork whose
whole method is *run the thing* should produce a usable backtrace. That is why
`openclonk` is 105 MB.

### Running the Linux client

```sh
tar xzf openclonk-9.0-alpha-fork.1-client-linux-x86_64-qt5.tar.gz
tar xzf openclonk-9.0-alpha-fork.1-game-data.tar.gz
cd openclonk-client-linux-x86_64-qt5
mkdir planet && mv ../openclonk-game-data/*.oc* planet/
./openclonk
```

`C4Reloc` looks for a `planet` directory next to the executable, which is what
that layout is. The binaries are linked against `ubuntu-latest`'s libraries and
need the runtime halves of libepoxy, SDL2, OpenAL, ALUT, Ogg/Vorbis, libpng,
libjpeg, freetype, curl, miniupnpc and Qt5 (or Qt6) present on the system.

That layout was checked rather than assumed: a client started against exactly
these archives loads the packed graphics, creates a GL context and reaches the
menu, and the headless server runs `Movement.ocs` out of them to 3 of 3
assertions passed.

**Music takes one more step on Linux**, and the log says why:

```
Music File not found: /usr/local/share/games/openclonk/Music.ocg
```

`C4MusicSystem` looks for `Music.ocg` under `SystemDataPath` — the install
prefix on Linux, not the executable's directory — so putting it in `planet/`
with the rest does nothing. It also looks under `UserDataPath`, and that one is
yours:

```sh
cp ../openclonk-game-data/Music.ocg ~/.clonk/openclonk/
```

The client then logs `Music: UrbanBolero.ogg` rather than the line above. The
underlying defect is [#28](https://github.com/eeryinkblot/openclonk/issues/28),
which is about the engine finding its own music, not about this archive.

### The macOS bundle is not distributable

It builds, it verifies, and it very probably will not run on your machine.
`tools/osx_bundle_libs` re-anchors rpaths to absolute paths on the build
machine, and the signature is ad-hoc rather than a Developer ID, so Gatekeeper
refuses it anywhere it was not built. It is published for inspection, not for
playing. [#24](https://github.com/eeryinkblot/openclonk/issues/24).

The macOS command-line tools have the milder version of the same problem: they
are unsigned, so a downloaded archive carries a quarantine attribute. Remove it
with `xattr -dr com.apple.quarantine <dir>` if you trust the build.

## Known limits

- No Windows client is built anywhere, in CI or here. Windows gets the headless
  engine and the tools only, though a client and the Qt5 editor have been built
  and run by hand on a Windows machine.
- `ObjectInteractionMenu.ocs` fails 14 of its 328 assertions, on all three
  platforms identically, cause not established
  ([#51](https://github.com/eeryinkblot/openclonk/issues/51)).
- Twelve places where the engine relies on undefined behaviour are located and
  pinned, none of them fixed
  ([#56](https://github.com/eeryinkblot/openclonk/issues/56)). ASan reports
  nothing.
- Seven of 99 scenarios do not link cleanly
  ([#55](https://github.com/eeryinkblot/openclonk/issues/55)).
- The Qt editor is compiled on Linux and Windows and started by nothing
  ([#46](https://github.com/eeryinkblot/openclonk/issues/46)).
- The 69 real game scenarios are loaded and linted; nothing asserts what they
  *do*, because they carry no `doTest()`.

## Building from source

`README` covers the general case, with the caveat that it still names C++14 as
the requirement — the project moved to C++17 in this fork. The three machines it
is developed on — macOS/Apple Silicon, Arch Linux, and Windows/MSVC — each
have a section in `CLAUDE.md` with the exact invocation, the dependencies
nothing else pulls in, and the traps that cost time on each.
